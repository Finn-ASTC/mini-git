## 结论与 skill 缺陷清单

- **可复现的 skill 缺陷**（本轮新增）：
  - P30 🟠 测试把证据追加写进仓库 → 交付验收被正确挡住（产品向，已修；抓到它的机制值得保留）
  - P31 🟡 制品 sha256 跨路径不可比（`[profile.release] debug=1`）→ 「冻结制品哈希」会假红
  - P32 🟢 验证者自建 cwd 不可能有开工前基线，而流程要求 `V_BASELINE`
  - P33 🟢 lease token 随 `claim` 回复返回并落盘在 job history（可 0 秒取回，不必等租约到期）
  - P34 🟢 验证者脚手架判定失败仍 `exit 0`（控制方必须解析报告，不能信退出码）
- **流程缺陷**：W7-S1（验证轮排在交付之前）、W7-S2（tmpfs 被打满，连沙箱都起不来）——见 `defects.md`。
- **本轮的模板改动建议**（下一 wave 用）：
  1. 任务包必须写清**依赖顺序**：验证轮的输入是「上一轮交付物 + 封存快照」，交付没到位就不许起飞。
  2. 验收计划模板固定四件套：**已知正确 + 故意错误（要求具体失败集合）+ 环境/落盘副作用 + 可复现性**。
  3. 「制品绑定」从 sha256 改成 **`.text` 段哈希 + 可选 `--remap-path-prefix` 重建**。
  4. 交付验收（含网络/绑定类测试）必须在**不受限宿主环境**里跑；沙箱内会得到系统性假红
     （本轮第一次 verify 就是这么失败的：540/22/1，attempt 保留在 `verify-3_oq4pj8`）。
  5. 每轮结束由控制方回收 `CARGO_TARGET_DIR`；`deliveries/` 快照不删。

**结论：这个规模下，多 agent 确实明显贵**

- 直算浪费：一次单 agent 会话做这 28 行 + 跑门禁，典型量级是 1–2M input、30–60K output。
  本阶段 input 高出约 **30–50 倍**，output 高出约 **5–10 倍**。
- 但是有实测到的回报（不是自说自话）：
  1. W7-D1（测试套件往仓库追加写、导致仓库过不了 `kind=delivery` 验收）是**被交叉验收抓到的**，
     作者自己的门禁全绿；单 agent 跑完 `cargo test` 会照常交付一个不可验收的仓库。
  2. P24 的修复必须在 **release** 下才暴露，作者原有门禁不覆盖这条路（这正是 P24 能熬过多轮的原因）；
     验证者自建脚手架 + 修复前制品负对照，把「修好了」从断言变成可复现证据。
  3. 若走单 agent 路线，这两条只能靠人肉补，成本是人工时间。
- 明确该砍的：W7-S1（V1 claim 后未发送即取消，纯开销）、两条 watch 的 8 条事后结清、
  以及控制方自身的 43M input——**编排侧记账才是最大的单项，而不是 worker 的重复劳动**。
- 模板建议：工作量小于 ~50 行时，用「1 作者 + 1 验证者，无独立返工轮」的轻量模式，
  并把控制方自己的巡检频率降下来（本轮控制方 172 次调用/轮，主要花在 watch/协议簿记）。
